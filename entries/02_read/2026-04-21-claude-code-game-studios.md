# Claude Code Game Studios: 49体のAIエージェントでゲームスタジオを構築するOSSテンプレート

## 3行要約

- Claude Code を本物のゲームスタジオに見立て、ディレクター・部門リード・スペシャリストの3階層に分かれた49体の専門AIエージェントと72のワークフロースキルを提供するOSSテンプレート（MIT）。
- エージェントはゲーム開発の全工程（企画・プログラミング・アート・オーディオ・QA・プロダクション）をカバーし、スタジオの組織構造と意思決定フローを模している。
- 人間は方向性の決定と確認だけを行い、エージェントチームが設計・レビュー・コミット品質チェックを自律的に実施する「ワンオペAAAスタジオ」を目指した設計。

## 自分への関連度: A

ゲーム開発20年のバックグラウンドと Claude Code 日常使用の両方が刺さる。Unity プロジェクトにそのまま適用できるかは要検証だが、CLAUDE.md 設計・Skills 構成・エージェント階層の実例として参考価値が高い。現在の開発ワークフローを大きく変える可能性あり。

## 感想・考察

**49体という数字について：**
ゲーム開発の役割を細かく分割した結果その数になっただけで、特に革新的な点はない。エージェント数が多いこと自体はセールスポイントにはならない。

**アート制作について：**
technical-artist エージェントは「最終アート資産の作成はしない」と明示されており、シェーダー開発・アセットパイプライン構築・技術検証が役割。3Dモデリングやテクスチャ制作は完全に人間側の作業として前提されている。アート制作が考慮に入っていない時点で、アート工程を重視するプロジェクトではほぼ意味がない。

**レベルデザインについて：**
level-designer エージェントができるのはレイアウト設計（ASCII・文字描写形式が想定）、敵配置、難易度曲線、導線設計など「設計書・仕様文書を作るところまで」。Elden Ring のような複雑な3D地形・ダンジョン構造を実際に組む作業は対象外。

**総括：**
このシステムが得意なのは「コード・設計文書・仕様書の生成」であり、「企画〜プログラミング」工程には強いが「アート〜レベル実装」工程はほぼノータッチ。エントリの関連度は A としたが、実態は B 程度。CLAUDE.md やエージェント階層の設計例として参考にする程度にとどめる。

「AAAスタジオに勝てる」「一人で AAA ゲームを作れる」という訴求は完全な誇大広告。アート・サウンド・レベル実装など制作工程の大部分は人間がやる前提であり、このシステムが自動化できるのはコードと仕様書の一部にすぎない。

**エンジニアの役割を細かく分ける効果について：**

個人開発規模では体感しにくいが、専門化が効くのは以下のような場合：

- **システムプロンプトの絞り込み**: 「ネットワークコードには触れるな」「ECS パターンを優先しろ」など専門的な制約を注入でき、判断が散漫になりにくい
- **並列実行前提の設計**: 別エージェントに分けると同時並行で走らせやすい（1体が全部やると直列になる）
- **責任範囲の明確化**: 大規模コードベースで意図しない改変を防ぐ

逆に個人開発では、コードベースが小さければ1体で全体を把握でき、調整コストが逆にオーバーヘッドになる。現状の Claude Code は1エージェントでも文脈切り替えが十分得意。Game Studios は「大規模チームの組織構造をそのままエージェントに写した」設計で、メリットが後付けになっている側面がある。

**役割を与えることの実装・レビュー精度への効果：**

効果はあるが、本質は「役割名」ではなく**役割に付随する具体的な制約・判断基準がシステムプロンプトに書かれているか**。

| 要因 | 効果 |
|------|------|
| 役割ラベルだけ | 小さい |
| 役割 ＋ 具体的な制約・観点の列挙 | 中〜大きい |
| 役割 ＋ ドメイン固有のサンプルや規約 | さらに大きい |

個人開発では常設のスペシャリストエージェントを用意しなくても、「ネットワークの競合状態とパケットロス耐性の観点でレビューして」のようにその都度観点を指定するだけでほぼ同等の効果が得られる。Game Studios 的な構成が有利になるのは、同じ観点を繰り返し大量に適用する規模感のプロジェクト。

## エンジニア役割細分化の追加考察（セッション 2026-04-24）

### 各エンジニアエージェント定義の実態

`gameplay-programmer` `network-programmer` `ai-programmer` `engine-programmer` `tools-programmer` `ui-programmer` の6種類＋ `lead-programmer`。各定義には共通して以下が埋め込まれている：

- **What This Agent Can Do**（やる）
- **What This Agent Cannot Do**（明示的にやらない）
- **Coordinates With / Escalation Path**（誰に渡すか）
- 領域固有の制約（例：`ai-programmer` は「2ms per-frame budget」、`network-programmer` は「Server is authoritative」「lag compensation up to 150ms」）

単に名前を分けたのではなく、**領域ごとに違う制約・ベストプラクティス・禁止事項をシステムプロンプトに焼き込んでいる**のが本質。

### 役割分割で得られる具体的効果

1. **ドメイン知識の濃度を上げられる**：汎用エージェントだと均等な指示しか出せないが、専門化すると領域の前提を強く埋め込める
2. **越境して低品質コードを書かれるのを防げる**："Cannot do" が品質ガードレールとして機能（gameplay が片手間でネットワーク同期を書く事故を防ぐ）
3. **親コンテキストを汚さない**：subagent 呼び出しなら大量の参照資料を読ませても結果だけ戻る
4. **並列実行が成立する**：UI／ゲームプレイ／ネットワークが論理的に独立していれば3エージェント同時実行が可能
5. **レビューの客観性**：実装者と別エージェントがレビューする構図を機械的に作れる
6. **ハンドオフの可視化**：誰の仕事かが組織図として明確化

### 役割分割の最大の弱点：クロスカット領域

ネットワーク同期前提のゲームプレイ（予測＋ロールバック、レプリケーション可能な状態マシン、RPC 発火スキル等）は、本質的に「ゲームプレイ実装」と「ネットワーク設計」が同じコードに織り込まれる領域。にも関わらず：

- `gameplay-programmer`: 「Write networking code」は禁止
- `network-programmer`: 「Modify non-networking game logic」は禁止

→ どちらも書けない領域が発生する。

**テンプレートの想定解**：`network-programmer` がレプリケーション抽象層・契約（`IReplicatedState` 等）を先に設計 → `gameplay-programmer` はその抽象に対して実装、という分業。Unity Netcode for GameObjects や UE Replication System のように抽象化が綺麗な前提なら成立する。

**現実に残る問題**：
- 抽象層が薄い／自前実装が多いプロジェクトでは破綻
- ハンドオフのラウンドトリップでステップ数が肥大化
- 境界紛争（曖昧領域でどちらも手を出さない／両方が触る）
- 逐次化（ネットワーク層完成前にゲームプレイが書けず、並列性が逆に下がる）

### 採用判断の基準

役割分割は **「クロスカット領域がレイヤ抽象で綺麗に隠蔽できる」プロジェクトを暗黙の前提**にしている設計。自前ネットコード・低レイテンシ要求のアクションゲーム・ロールバック実装などでは、役割分割が逆に開発を難しくする。

判断基準は**コードベースの抽象境界の綺麗さ**。現状「区別せずに問題を感じない」のは、スケール・抽象境界の状況に照らして妥当。導入するとしても全部入れず、自分のプロジェクトで境界を引きたい1〜2領域だけ切り出すのが現実的。クロスカットが多い領域を切り出す場合は、`networked-gameplay-programmer` のようなハイブリッド役割を作るか、"Cannot do" 制約を緩めるカスタマイズが必要。
