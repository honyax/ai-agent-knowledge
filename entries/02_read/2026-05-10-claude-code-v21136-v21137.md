# Claude Code v2.1.136 / v2.1.137 — MCP サイレント消失修正・OAuth トークンレース修正・Windows VSCode 拡張のアクティベーション失敗修正

## 3行要約

- v2.1.136（2026-05-09 前後）: 重要バグ修正が中心。**`.mcp.json`・plugins・claude.ai connectors が `/clear` 後にサイレント消失する問題**（VS Code 拡張・JetBrains プラグイン・Agent SDK で発生）を修正。並行クレデンシャル書き込みで rotate 直後の OAuth トークンが上書きされる **ログインループ** を修正。複数 MCP サーバの **OAuth refresh token を並行リフレッシュで失う問題** も解消
- 新機能: `CLAUDE_CODE_ENABLE_FEEDBACK_SURVEY_FOR_OTEL` 環境変数で OpenTelemetry 経由のセッション品質サーベイを再有効化（エンタープライズ向け）。**`settings.autoMode.hard_deny`** 設定で auto mode 分類器を無条件ブロックするルールを定義可能
- v2.1.137（2026-05-10 前後）: 単発リリースで **VSCode 拡張が Windows でアクティベートに失敗する** バグの hotfix。Windows ネイティブ拡張ユーザにとって必須アップデート

## 自分への関連度: A

VSCode ネイティブ拡張環境ユーザとして、特に v2.1.137 の Windows extension activation 修正は直撃。さらに v2.1.136 のうち以下が直接効く:

- **`.mcp.json` / plugins / connectors が `/clear` 後に消える問題の修正**: 自分は `/catch-up` でしばしば `/clear` を使う運用。これに直撃していた可能性が高い
- **OAuth ログインループの修正**: v2.1.126 で wake-from-sleep の race を直したのに、まだ別経路で残っていたバグ。「並行クレデンシャル書き込み」は SSO 環境で起きやすい
- **`settings.autoMode.hard_deny`**: 自動承認モード時に「絶対に通すな」ルールを宣言できる。`/fewer-permission-prompts`（同日エントリ）が allow を組むのに対し、こちらは deny の最上位。組み合わせる価値が高い
- **`Edit(...)` allow ルールがある時に plan mode が file write を止めないバグ修正**: plan mode 運用しているなら重要

## 詳細

### v2.1.136 — 新機能

- **`CLAUDE_CODE_ENABLE_FEEDBACK_SURVEY_FOR_OTEL`**: OpenTelemetry で回答を取りたいエンタープライズ向けにセッション品質サーベイを再有効化する環境変数
- **`settings.autoMode.hard_deny`**: auto mode 分類器に対する無条件ブロックルール。auto mode が「これは安全」と判断しても、`hard_deny` パターンに一致するツール呼び出しは強制拒否される

### v2.1.136 — 重要バグ修正

- **MCP サーバの `/clear` 後サイレント消失**: `.mcp.json` 由来・プラグイン由来・claude.ai connectors 由来の MCP サーバ設定が、`/clear` 後に黙って消える問題。VS Code 拡張・JetBrains プラグイン・Agent SDK で発生していた
- **OAuth ログインループ**: 並行クレデンシャル書き込みが、リフレッシュ直後の有効な OAuth トークンを上書きして「再ログイン強制」のループに陥るレア競合を修正
- **複数 MCP サーバの OAuth refresh token ロス**: 複数 MCP が同時に refresh すると token が消える問題
- **extended thinking + redacted thinking ブロック後の 400 エラー**: tool call の後に redacted thinking が出る組み合わせで API エラー
- **`--resume` / `--continue` がアンダースコア入りパスでセッションを見つけられない問題**
- **plan mode が `Edit(...)` allow ルール一致時に file write をブロックしない**: plan mode の本来の役目を回復
- 各種レンダリング・file picker・permission ダイアログ・ターミナル互換（WSL2・各 emulator・IDE 統合）の修正

### v2.1.137（hotfix）

- **VSCode 拡張が Windows でアクティベートに失敗する問題** を単発で修正。Windows ネイティブ拡張ユーザは v2.1.137 へ即アップデート推奨

### v2.1.134 / v2.1.135 について

npm に publish されず、v2.1.133 から v2.1.136 へ直接ジャンプ（内部ビルド扱い）。

### `/fewer-permission-prompts` × `hard_deny` の組合せ

同日生成エントリ（2026-05-10-fewer-permission-prompts-skill.md）の allowlist と、本リリースの `settings.autoMode.hard_deny` を組み合わせると:

| 層 | 役割 |
|-----|------|
| `permissions.allow`（`/fewer-permission-prompts` 推奨） | 安全な read-only を自動許可 |
| `permissions.deny` | 明示的に禁止する操作 |
| `settings.autoMode.hard_deny` | auto mode の判断を上書きして強制拒否 |

の三層構造で、approval fatigue を下げつつ安全性を保つ運用が成立する。

## 試すなら

1. `claude update` で v2.1.137 にアップデート（Windows ユーザ必須、それ以外は v2.1.136 でも可）
2. `/mcp` で MCP サーバ一覧を確認し、`/clear` 後も保持されているか動作確認
3. auto mode を使うなら `settings.autoMode.hard_deny` に `Bash(rm -rf*)`、`Bash(sudo:*)` 等を追加
4. OAuth でログインしている場合、再ログインループ症状（複数デバイスで頻発）が出ていなければ確認なしで OK
5. plan mode を使う運用なら、`Edit(...)` allow がある状態で plan mode に入っても file write が止まるか確認

## 感想・考察

### 注目すべき追加機能

特に注目したのは以下:

- **`settings.autoMode.hard_deny`**: auto mode 専用の最終防衛ライン。通常の `permissions.deny` とは別の階層で、auto mode 分類器が「安全」と判断したものでも強制拒否できる。同日エントリの [`/fewer-permission-prompts`](../01_unread/2026-05-10-fewer-permission-prompts-skill.md) で allowlist を広げる運用と**セットで設計する**ことで、approval fatigue を下げつつ最後の安全弁を確保できる
- **plan mode + `Edit(...)` allow ルールのバグ修正**: plan mode の信頼性そのものに関わる修正。plan mode を再評価するならこのバージョン以降が前提
- **`.mcp.json` / plugins / connectors の `/clear` 後消失バグ**: エラーが出ずサイレントに動かなくなる典型的な「気づきにくい」バグ。`/catch-up` で `/clear` を多用する自分の運用では直撃していた可能性が高い

### plan mode を明示的に使うメリットの再考

`Edit(...)` allow 時の plan mode バグ修正をきっかけに、plan mode の価値を整理し直した。

**plan mode の本質的メリット**:

1. **ハーネスレベルで edit/write が強制ブロックされる**: プロンプトで「計画してから実装して」と書いても、モデルが勢いで Edit を呼ぶリスクは残る。plan mode はツール呼び出し自体が拒否されるので、暴走の物理的遮断になる。Opus は「ついでに直しちゃう」傾向があるので、**リファクタや破壊的変更が絡むタスク**では価値が高い
2. **`ExitPlanMode` という設計された承認ポイント**: 計画 → 承認 → 実行の遷移が UI で明示され、境界がはっきりする
3. **「まだ書かないで」をプロンプトに書かなくて済む**: context window の節約と指示の確実性

**プロンプト指示型のメリット**:

1. **出力フォーマットを完全に制御できる**: 自分は独自の計画フォーマットを使う運用なので、`ExitPlanMode` のテキストフィールドに収める形だと厳密に守らせるのが難しい
2. **副作用ありの探索コマンドが使える**: ビルドを通してエラーを見る、テストを走らせて failing case を確認、`npm install` してから API を読む、など。plan mode だと封じられる
3. **モード切替の摩擦がない**: Shift+Tab → ExitPlanMode → 続行、の3ステップが不要

**使い分けの結論**:

| 状況 | 推奨 |
|------|------|
| 既存コードの破壊的変更・大規模リファクタ | plan mode |
| Claude が勢いで実装に走るのを物理的に止めたい | plan mode |
| 独自フォーマットの計画書を出したい | プロンプト指示型 |
| ビルド・テスト・パッケージ調査を計画段階でしたい | プロンプト指示型 |
| 短く明確なタスク | どちらも不要 |

「毎回 plan mode」ではなく「**ヤバそうな時だけ plan mode**」のハイブリッド運用が現実解。現状の通常モード+独自フォーマット運用は維持しつつ、破壊的変更を伴うタスクの安全弁として plan mode を選択的に併用する。
