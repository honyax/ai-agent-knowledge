# LLM Wiki: Karpathy が提案する「LLM が自律維持するナレッジベース」パターン

## 3行要約

- 従来の RAG（質問のたびに生ドキュメントから検索）ではなく、LLM が Markdown Wiki を段階的に構築・更新し続ける「LLM Wiki」パターンを Andrej Karpathy が提案。
- 生データ層・Wiki 層・スキーマ層の 3 層構成で、新ソースを追加するたびに LLM が既存ページと統合し矛盾を記録する。人間が嫌がるブックキーピングをLLMに委譲するのがコアアイデア。
- スケール課題（100〜200ページ超でコンテキスト超過・知識漂流リスク）も議論されており、知識グラフ組み合わせや階層インデックスなどのハイブリッド改善案が提案されている。

## 自分への関連度: A

このリポジトリ自体がほぼ「LLM Wiki」の実践であり、設計の参考になる。エントリの自動統合・矛盾検出・インデックス肥大化への対処は将来的な課題として直結する。今すぐ実装に使うというよりは、ナレッジベース設計の指針として読む価値が高い。

## 詳細

**3層アーキテクチャ:**

| 層 | 役割 |
|----|------|
| 生データ層 | 不変のソース文書（変更しない） |
| Wiki 層 | LLM が生成・管理する Markdown ページ（クロスリファレンス付き） |
| スキーマ層 | Wiki の構造とワークフローを定義する設定ドキュメント |

**主な操作:**
- **取り込み（Ingest）**: 新ソースを処理し、複数の Wiki ページを更新・統合
- **クエリ**: 生データではなく Wiki から答えを合成
- **メンテナンス**: 矛盾・古い情報のチェック

**スケール上の既知の課題:**
- 約 100〜200 ページ超で `index.md` 全体がコンテキストウィンドウを超過
- 400 ページ超のソース文書は取り込み前に事前検索が必要
- 矛盾解消ポリシーが仕様として未定義
- Wiki 成長に伴うトークン膨張で最終的に破綻するという指摘あり

**コミュニティ提案の改善策:**
- 人間が定義したエンティティ型 ＋ LLM が接続を生成するハイブリッド構成
- 矛盾に信頼スコアを付けた知識グラフ
- 必須 Markdown 生成ではなくオプトイン型 Wiki ポインタ

## 試すなら

1. Gist 本文を読み、3 層構成のディレクトリ設計を把握する
2. 小規模（10〜20 ページ程度）のトピックで Wiki 層を手動設計してみる
3. 新ソース追加時に LLM に「既存 Wiki との統合」を指示するプロンプトを実験する
4. index.md の肥大化が起きたらスキーマ層で階層インデックスに切り替える設計を検討
5. このリポジトリの `entries/` 構造との差分・共通点を整理して設計フィードバックを得る

## 感想・考察

LLM Wiki の新情報取り込みは「ユーザーがファイルを置いて LLM に処理を指示する」手動トリガー方式のみ。自動スケジューリングや RSS 連携は提案されていない。

これは意図的な設計で、「量より質」の思想が根底にある。手当たり次第に取り込むのではなく、自分が重要だと判断したものだけを Wiki に入れたいという発想。結果として情報の取りこぼしは多いが、Wiki に残る内容の質は高くなる。

このリポジトリの `/catch-up` スキルとの比較：

| | 手動トリガー（LLM Wiki） | 自動収集（このリポジトリ） |
|--|------------------------|--------------------------|
| 情報の質 | 高い（自分でフィルタ） | バラつきあり（AIが選別） |
| 取りこぼし | 多い | 少ない |
| 維持コスト | 意志力が必要 | 低い |
| 対象 | 深く理解したいもの | キャッチアップ全般 |

LLM Wiki は「本を読み終えたら Wiki に統合する」に近い使い方を想定しており、「RSS を全部読む」とは別物。実用上は「自動で集めて、重要なものだけ手動で Wiki に昇格させる」2段階構成が現実的な落としどころに思える。このリポジトリで言えば、`03_todo` や `04_tried` まで昇格したエントリを LLM Wiki 的な統合ページに集約する、という使い方が相性よさそう。

**Q&A は Wiki を更新しない設計について:**

質問（クエリ）は Wiki を更新しない。取り込み（Ingest）と クエリ（Query）は明確に分離されており、クエリは Wiki を読むだけで書き込まない。

これは意図的な判断で、理由は以下の通り：
- 回答が間違っていた場合に Wiki が汚染される
- 「誰かが聞いたこと」と「信頼できるソースに書いてあること」は別物
- Wiki の品質保証には入力元の信頼性管理が必要

「会話ログも取り込み対象のソースとして扱う」拡張は技術的には可能。このリポジトリの `/try` で実践結果を手動追記する運用が、それに近い考え方。
