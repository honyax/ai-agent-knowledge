# Claude Codeをチームで運用するためのCLAUDE.md設計とカスタムエージェント分担

## 3行要約

- チームでのClaude Code運用では「何を覚えさせるか」より「何を覚えさせないか」が重要で、コード読解で判明する内容はCLAUDE.mdに書かないことでメンテナンス負荷を下げる。
- CLAUDE.mdは「ユーザーグローバル（個人設定）」「リポジトリ直下（プロジェクト不変ルール）」「サブディレクトリ（区画固有ルール）」の三層構造で整理し、エージェント分担はスラッシュコマンド（定型プロンプト）とサブエージェント（独立した責務）を役割で区別する。
- MCPサーバー（モデルが文脈判断するDB操作・情報検索）とフック（lintチェック・ファイル保護などの決定論的処理）の選別基準と、ルール肥大化・エージェント過剰分割・フックによる過度な制限の3つの典型的な失敗パターンを整理。

## 自分への関連度: A

現在の個人運用（グローバルCLAUDE.md＋プロジェクトCLAUDE.md）を将来チーム設定に拡張したり、自分のエージェント分担設計を見直すための実践的な指針が得られる。特に「MCPかフックか」の判断基準は自分の今後のhooks活用検討（[[user_hooks_usage]]）と直結する。「スラッシュコマンドはカスタムSkillで代替できる」という整理も、自分の既存Skills設計の見直しに効く。

## 詳細

### CLAUDE.mdの三層構造
| レベル | 内容の例 |
|--------|---------|
| ユーザーグローバル | 言語設定、git操作の確認方針 |
| リポジトリ直下 | アーキテクチャ方針、不変ルール |
| サブディレクトリ | フロントエンド固有の規約など |

**設計原則**: 「コード読解で判明する内容は記載しない」。メンテナンス負荷を下げ、判断鈍化を防ぐ。

### エージェント分担の判断基準
- **スラッシュコマンド（カスタムSkill）**: 定型プロンプト、手順の定式化
- **サブエージェント**: メイン文脈から分離する価値があるもの
  - 大量ファイル探索（文脈圧迫回避）
  - 専門的役割（レビュアー、テスト作成）
  - 並列実行可能なタスク

### MCPかフックかの判断軸
- **MCPサーバー**: モデルが文脈に応じた判断をする必要がある場合（DB操作、情報検索など）
- **フック**: 「絶対実行」「禁止事項」など決定論的な処理（lintチェック、ファイル保護）

### 典型的な失敗パターン
1. **ルール文書の肥大化**: 判断鈍化につながる
2. **エージェント過剰分割**: コスト増加
3. **フックによる過度な制限**: 自己修復能力の喪失
4. **個人設定とチーム設定の混在**

→ チーム導入では「定期的な棚卸し」が運用継続のカギ

## 試すなら

1. 自分の現在のCLAUDE.md（グローバル・プロジェクト）を棚卸しし、「コード読解で判明する内容」を削除する
2. 既存の自作Skillsをレビューし、「スラッシュコマンド（定型プロンプト）」と「サブエージェント（独立した責務）」の分類を見直す
3. 現在hooksを使っていない処理の中に「決定論的に実行したい」ものがあれば、MCPではなくフックに移す候補を洗い出す
